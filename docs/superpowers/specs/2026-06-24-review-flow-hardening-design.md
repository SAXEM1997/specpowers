# specpowers-review 审查流程强化

## 概述

对 specpowers-review 多模型渐进式审查流程中的 Steps 3-5 做两项强化：Step 3 监督 Agent 从可选改为强制交叉验证；Step 4 修复执行者从主 Agent 改为子 Agent。

## 架构决策

### 决策 1：Step 3 监督 Agent 强制化

**之前**：Step 3 标注"推荐，可跳过"，有两个跳过条件（单一模型、简单文档 <50 行）。

**之后**：Step 3 强制执行，不可跳过。单一模型时使用同模型执行并在报告中声明。

**理由**：主 Agent 合并三路报告时存在固有的"合并偏差"——遗漏、过度合并、误判都是常见问题。强制交叉验证通过独立视角审查合并质量，是防止主 Agent 错漏的关键防线。

### 决策 2：修复由子 Agent 执行

**之前**：Step 4 由主 Agent 逐条执行修复。

**之后**：Step 4 由独立修复子 Agent 执行修复，主 Agent 仅逐条校验修复质量（不直接修改代码/文档）。

**理由**：主 Agent 在 Step 2 中已经深度参与合并判断，对问题和修复方案有强烈预期。由同一 Agent 执行修复容易产生"确认偏误"——自我验证时更难发现自己的修复错误。子 Agent 独立执行修复，主 Agent 以审查者身份校验，形成"修复→审查"的独立双人检查。

## 修改设计

### 上下文传递机制

独立子 Agent 无法访问主 Agent 会话上下文。不使用文件持久化（增加路径管理和读写逻辑），而是通过 Agent 工具的 `prompt` 参数**直接注入**所需上下文——这是 Claude Code Agent 工具的原生模式。

| Step | 注入内容 | 接收方 |
|------|---------|--------|
| Step 3 | 三份原始审查报告全文 + 最终合并判断表 | 监督 Agent |
| Step 4 | 最终合并判断表中标记为"接受"的修复项（修改指令 + 原文 + 新文本 + 位置） | 修复子 Agent |
| Step 5 | 修复子 Agent 的输出 + 主 Agent 的校验记录 | Quick Review Agent |

**截断策略**：当注入内容总长度超过 Agent prompt 限制时（通常 > 8000 字），自动应用降级策略：
1. 优先保留"问题清单 + 严重度 + 证据"部分（每份报告的核心发现），截断"分析过程"和"冗余上下文"
2. 截断处标注 `[... 已截断，完整报告已由主 Agent 在合并阶段审查 ...]`
3. 合并判断表不截断（核心参照物）

### Step 3: 独立监督 Agent 交叉验证（强制性）

```
Step 3 — 独立监督 Agent 交叉验证（强制，不可跳过）

主 Agent 将以下内容注入监督 Agent prompt:
- 三路 Agent 的原始审查报告全文（Step 1 产物）
- 主 Agent 的合并判断表（Step 2 产物）

监督 Agent 执行交叉比对:
1. 溯源检查: 合并判断表中的每条问题是否都能在原始报告中找到对应来源？
   无法溯源 → 标注 [无法溯源]
2. 遗漏检测: 原始报告中有但合并表中缺失的发现？
   逐条标注遗漏原因（被合并/被拒绝/被遗漏）
3. 合并去重合理性:
   该合并未合并 → [合并遗漏]
   不该合并被误合并 → [过度合并]
4. 判断充分性:
   主 Agent 的接受/拒绝/部分接受理由是否充分？→ 不充分标注 [判断存疑] + 建议
   严重度校准：当多个原始 Agent 对同一问题给出不同严重度时，Step 2 按"取最高级"规则统一。检查此校准是否合理（过度升级/降级）

输出独立审核报告: 每项标注 [维持/修正/补充] + 理由 + 建议

主 Agent 根据审核报告调整合并判断表，输出最终版。

降级: 仅单一模型可用时，使用与主 Agent 相同模型执行监督，报告中声明"单一模型，缺少独立视角交叉验证"，但不可跳过。独立上下文（子 Agent 看不到主 Agent 合并推理链）仍能捕获遗漏。
  简化规则: 合并后问题数 < 5 → 仅执行溯源检查 + 遗漏检测（维度 1-2）；≥ 5 → 完整四维度。
```

### Step 4: 子 Agent 执行修复 + 主 Agent 校验

```
Step 4 — 子 Agent 执行修复 + 主 Agent 校验

0. P0 用户确认 Gate:
   - 合并判断表中标记为"接受"的 P0 项，先提请用户逐条确认（问题判定 + 修复方案）
   - 用户确认后，方可将 P0 项纳入修复子 Agent prompt
   - P1/P2 项直接纳入修复 prompt，无需用户确认
   - 用户拒绝某项 P0 修复方案 → 标注为"用户拒绝"，保留在报告中但不修复

1. 指派修复子 Agent:
   - 模型选择: 优先与审查 Agent 不同模型（确保修复视角独立）；仅单一模型可用时使用同模型
   - Prompt 注入: 最终合并判断表中标记为"接受"的修复项（精确修改指令 + 原文片段 + 新文本 + 修改位置）
   - 职责边界: 修复子 Agent 只执行文件修改，不审查、不输出判断
   - 并行规则: 修复项 > 5 条时拆分为多个修复子 Agent 并行执行
     分组前检查跨文件语义依赖（如同一术语在不同文件中的统一替换、跨文件交叉引用的同步更新）→ 存在依赖的修复项分配给同一子 Agent → 无依赖的按修改文件分组，确保不同子 Agent 不修改同一文件

2. 主 Agent 逐条校验:
   - 每条修复是否按修改方案正确应用？（原文→新文对比）
   - 修复是否引入了新问题？（残留旧术语、格式破坏、Markdown 语法错误）
   - 全文 grep 验证：废弃概念/术语已清除，无残留占位符

3. 校验不通过 → 标注失败项 → 修复子 Agent 重新修复 → 主 Agent 再次校验（最多重试 3 轮，超过则标注"修复失败"并提请用户裁决）
4. 全部通过 → 进入 Step 5

降级: 子 Agent 工具不可用时（极端环境），退回主 Agent 自行修复，报告中声明限制。环境不支持并行 Agent 时，修复子 Agent 改为串行执行，拆分规则不变，报告中声明"串行执行（环境限制）"。
```

### Step 5: Quick Review 收尾（微调）

通读对象从"主 Agent 的修复结果"改为"修复子 Agent 的输出 + 主 Agent 的校验记录"（通过 prompt 注入 Quick Review Agent）。其余不变。

## 不做修改

- Point 1（多轮循环强制化）：保持当前建议性收敛提醒，不改
- UltraReview 流程：本次仅修改多模型渐进式审查流程，UltraReview 的 Step A-F 协议不在本次修改范围
- 收敛提醒机制、最终通读 Gate：不变
- UltraReview 的 Step A-F 协议存在与多模型渐进式同构的合并偏差和确认偏误风险。本次强化模式（监督 Agent + 子 Agent 修复）将在后续版本中同步应用到 UltraReview。
